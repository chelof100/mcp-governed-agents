% --- Abstract -----------------------------------------------------------------
\begin{abstract}
\noindent
Governing an LLM agent at runtime requires identity-bound,
cryptographically verifiable human authorisation to resolve persistent
halt states (P8). The deployment question that remained open is:
\emph{how does the governance stack reach an agent without modifying
the agent's code?}

We answer this question by positioning the governance stack at the
\emph{Model Context Protocol} (MCP) layer.
We introduce the \emph{MCP Governance Proxy} ($\Proxy$), a stateful
\emph{protocol-layer governance control plane} that intercepts tool
calls between any MCP-compatible agent client and any MCP server,
applying the P7--P8 governance stack
(IML\,+\,RAM\,+\,Recovery Loop\,+\,APB) transparently.
The design requires no modification to the agent client or server: the
proxy is a drop-in addition to the deployment topology. (The evaluation
drives the governance interceptor \emph{in-process}; it has not been run
against a third-party MCP client---see \S\ref{sec:discussion}.)
This positions governance at the protocol boundary rather than inside
the agent, in the manner of service meshes for microservice traffic.

We state three results.
\emph{Transparency} (T9.1) states that on the non-halt
path the proxy forwards requests and returns results unchanged; it
holds by construction for a stateless server and is stated as such.
\emph{Halt latency} (T9.2) decomposes the time to emit a halt into
$\Dnet + \Dverify + \Dpolicy$; it is a decomposition, not a bound on
$\Dpolicy$, which depends on the drift monitor. \emph{Multi-Hop
Authority Propagation} (T9.3) states that, \emph{under an explicit
attribution axiom}, in Agent-to-Agent (A2A) delegation chains the
required APB is the one registered for the \emph{originating} agent,
and the delegation chain is recorded in the evidence block. The chain
itself is not authenticated (no delegator signs it); see the threat
model.

We evaluate the construction with five experiments, all in-process
and with a simulated agent (\texttt{MockLLM}) and a simulated
auto-approving human.
\emph{E1}~(latency): $10{,}000$ governed calls; the windowed IML monitor
has a P95 \emph{decision} overhead of $51.8\,\si{\micro\second}$ against an
in-memory call (not the overhead of real stdio/JSON-RPC transport).
\emph{E2}~(\texttt{MockLLM} agent, $5$ seeds $\times$ $200$ steps): $310$
HALT events; every APB verifies. A live-LLM variant was not run.
\emph{E3}~(multi-hop A2A, depths $1$--$5$): $334$ HALT events; the
configured chain is copied into the evidence block in $100\%$ of cases.
\emph{E4}~(concurrency, independent sessions): $N \in \{1,4,16,64\}$
threads, $0$ exceptions.
\emph{E5}~(adversarial regression suite): the attack vectors
(wrong-key signing, evidence tampering, replay, revoked principal,
authority substitution, and a cross-call APB) are rejected; this is a
regression suite written by the author, not a measure of security.
A revision note (\S\ref{sec:discussion}) lists what an audit of the first
release found and what was changed or withdrawn.
\end{abstract}

\section{Introduction}
\label{sec:intro}

The \emph{Model Context Protocol} (MCP) \citep{anthropic2024mcp} has
emerged as a widely adopted protocol for connecting LLM-based agents to
external tools and data sources. An agent that speaks MCP can call any
MCP-compatible server without custom integration; the protocol handles
discovery, invocation, and result delivery uniformly. This uniformity
creates a deployment opportunity that prior work in this series did not
exploit: because all tool calls pass through a single, well-specified
protocol, a governance layer inserted at that protocol boundary
governs \emph{all} of the agent's external actions without modifying
the agent's code---instantiating, in effect, a
\emph{protocol-layer governance control plane} for LLM agents.

Paper~7 of this series \citep{fernandez2026applied} established an
integrated runtime governance stack that detects drift, applies the
Reconstructive Authority Model (RAM), and escalates persistent halt
events for human resolution. Paper~8 \citep{fernandez2026ibg}
formalised the \emph{Accountability Proof Block} (APB) as the
identity-bound, cryptographically signed record of those human
resolutions. Both papers explicitly identified MCP and A2A integration
as future work (P7~\S13, P8~\S10). This paper fulfills that commitment.

\paragraph{Problem.}
Deploying the P8 governance stack on an existing LLM agent requires
either (a) modifying the agent's source code to call the governance
layer at each tool invocation, or (b) wrapping the agent at a protocol
boundary that the agent already respects. Option~(a) is impractical
for agents whose code is unavailable, large, or managed by a third
party. Option~(b) is exactly what MCP enables.

\paragraph{Contributions.}
\begin{enumerate}[leftmargin=2em, topsep=2pt, itemsep=2pt]
  \item We define the \emph{MCP Governance Proxy} $\Proxy$ formally
        (\S\ref{sec:proxy}), giving its state, its per-call decision
        function, and its interaction with the P8 APB protocol extension.
  \item We state three results (\S\ref{sec:theorems}): Transparency
        (T9.1), a Halt Latency decomposition (T9.2), and Multi-Hop
        Authority Propagation under an explicit attribution axiom (T9.3).
  \item We provide a Python reference implementation on the official
        \texttt{mcp} SDK (\S\ref{sec:impl}), stdio transport only, with
        97 tests (61 inherited from P7+P8, 36 new).
  \item We add one thing to P8's evidence block: an optional action
        commitment $\ahash$ (hash of tool and arguments), so the
        principal's signature covers \emph{what} is approved.
  \item We evaluate the construction in-process with five experiments
        (\S\ref{sec:exp1}--\S\ref{sec:exp5}):
        E1~decision overhead, E2~\texttt{MockLLM} agent with a simulated
        human, E3~multi-hop A2A (depths 1--5), E4~concurrency, and
        E5~an adversarial regression suite.
\end{enumerate}

\paragraph{Relation to the series.}
This paper builds on P7 (the governance stack) and P8 (the APB); \S\ref{sec:background}
restates only what is needed to read the definitions here, and it is
brief: the internals of IML, the RAM gate and the Recovery Loop are not
re-derived, so judging \emph{what} the governance decision does requires
P7. P10 \citep{fernandez2026nbg} removes the blocking behaviour recorded
as Limitation~4.

\paragraph{Roadmap.}
\S\ref{sec:related} surveys related work.
\S\ref{sec:background} restates the minimal P7+P8 prerequisites.
\S\ref{sec:framework} defines the proxy formally.
\S\ref{sec:theorems} proves T9.1--T9.3.
\S\ref{sec:impl} describes the implementation.
\S\ref{sec:exp1}--\S\ref{sec:exp5} report the five experiments.
\S\ref{sec:discussion} discusses security analysis, limitations,
and extensions.
\S\ref{sec:conclusion} concludes.

\section{Related Work}
\label{sec:related}

\paragraph{MCP and agent middleware.}
The Model Context Protocol \citep{anthropic2024mcp} defines a
client--server protocol for tool discovery and invocation over stdio
and HTTP+SSE transports. Existing MCP deployments do not include a
governance layer; each tool is exposed and invoked directly. The
Agent-to-Agent (A2A) protocol \citep{google2025a2a} extends this to
multi-agent settings, allowing one agent to delegate tasks to another.
Neither protocol specifies how governance or accountability are
maintained across delegation chains.

\paragraph{Agent orchestration frameworks.}
LangGraph \citep{langgraph2024}, AutoGen \citep{autogen2023}, CrewAI
\citep{crewai2024}, and OpenAI Swarm \citep{openai2024swarm} provide
orchestration primitives for multi-agent workflows. They do not provide
identity-bound, cryptographically verifiable records of human authority
decisions at runtime. Our proxy is orthogonal: it can be inserted into
any of these frameworks at the MCP layer without modifying the
orchestration logic.

\paragraph{Runtime verification.}
Runtime monitoring \citep{leucker2009brief,havelund2004efficient,%
falcone2011tutorial} checks that running systems satisfy formal
specifications. Existing monitors observe system behaviour but do not
provide a mechanism for human authority decisions to be cryptographically
bound to the events that triggered them. The proxy extends runtime
monitoring with the identity-binding of the APB.

\paragraph{Middleware and proxies.}
The Proxy design pattern \citep{gamma1995design} is a standard approach
for interposing behaviour between a client and a server. Existing
governance proxies for web services (API gateways, service meshes)
enforce access control policies but do not maintain per-event,
per-principal accountability records. Our contribution is specific to
the LLM-agent governance problem: stateful drift detection, the RAM
authority model, and the APB all require state that general-purpose
proxies do not maintain. The present work occupies the same
architectural category---a \emph{governance control plane at the
protocol layer}---but for LLM-agent systems, with state requirements
specific to that domain.

\paragraph{Agent governance series.}
This paper is the ninth in a series
\citep{fernandez2026a,fernandez2026acp,fernandez2026iml,%
fernandez2026govstr,fernandez2026ram,fernandez2026opram,%
fernandez2026applied,fernandez2026ibg}. The series develops a formal
governance framework from first principles; this paper addresses the
\emph{deployment} question that completes the framework.

\section{Background}
\label{sec:background}

We restate the minimal prerequisites from P7 and P8. Readers familiar
with both papers may skip to \S\ref{sec:framework}.

\subsection{Design Constraints}

Two design constraints from P7 \citep{fernandez2026applied} are
inherited verbatim:

\begin{description}[leftmargin=2em, topsep=2pt]
  \item[DC.1 (Separation of Recalibration Authority).]
        For all $t$, $\Azero(t) = \Azero(0)$. The execution layer
        is forbidden from modifying its own admission baseline at
        runtime.
  \item[DC.2 (Drift Event Classification).]
        A halt is \emph{transient} if the drift estimator $\Dhat(\tau)
        \geq \theta$ for $\tau$ within a bounded window $\Delta T$ and
        returns below $\theta$ thereafter; it is \emph{persistent} if
        $\Dhat(t) \geq \theta$ for all $t \in [t_0, t_0 + \Delta T]$.
        Persistent halts constitute \emph{governance events}.
\end{description}

\subsection{Accountability Proof Block (APB)}

From P8 \citep{fernandez2026ibg}, an APB signed by principal $\Hi$ is:
\[
  \APB \;=\; (\Es,\;\Dh,\;\sigh)
\]
where $\Es = (\mathrm{hash}(\Azero),\,\Dhat(t_e),\,t_e,\,
\mathrm{hash}(\text{trace}_{\le t_e}),\,\text{cause},\,\text{event\_id}
[,\,\ahash])$
is the system evidence block, $\Dh = (\Hi,\,\text{decision},\,
\text{rationale},\,\text{scope})$ is the human decision block,
and $\sigh = \mathrm{Sign}_{\ski}(\mathrm{canon}(\Es) \Vert
\mathrm{canon}(\Dh))$ is the ed25519 signature. The last field
$\ahash = \mathrm{SHA\text{-}256}(\mathrm{JCS}(\{\text{tool},\,\text{args}\}))$
is \emph{optional} and new here (it originates in P10): P8's $\Es$ does not say
which call a halt concerns, so a signature did not cover \emph{what}
was approved. When $\ahash$ is absent it is dropped from the canonical
form, so P8 APBs are unchanged; the P9 proxy always sets it.

A verifier checks five predicates V1--V5: (V1)~signature validity,
(V2)~principal registered, (V3)~principal active at $t_e$,
(V4)~$t_e$ within replay window, (V5)~event\_id not previously seen
(replay resistance; part of the P8 verifier since its second version,
which is the one published on arXiv).
Theorems T8.1--T8.3 of P8 establish governance completeness,
non-repudiability, and impossibility of anonymous re-authorisation.

\subsection{Governance Stack}

The governance stack processes each tool call through three layers:
\begin{enumerate}[leftmargin=2em, topsep=2pt, itemsep=1pt]
  \item \textbf{IML Monitor}: computes $\Dhat(t)$ from the running
        tool-call trace using JS-divergence ($D_t$), mean risk score
        ($D_c$), and depth deviation ($D_l$), combined with EMA
        smoothing.
  \item \textbf{RAM Gate}: for tool calls with risk score RS\,$\ge 45$,
        checks authority components $\{I, B, R, C, E\}$ under partial
        observability and returns $\ADMIT$, $\HALT$, or $\DENY$.
  \item \textbf{Recovery Loop}: on $\HALT$, attempts up to $k$
        iterations with increasing state coverage.
        Returns $\RESUME$, $\HALT$, or $\texttt{ESCALATE}$.
\end{enumerate}
Persistent $\HALT$ or $\texttt{ESCALATE}$ from the Recovery Loop
constitutes a governance event requiring an APB.

\section{Formal Framework}
\label{sec:framework}

\subsection{MCP Tool Call Semantics}
\label{sec:mcp-semantics}

Let $\Sigma$ be a finite alphabet of tool names and $\mathcal{A}$
the space of argument dictionaries. A tool server $\mathcal{S}$ is
a function $\mathcal{S}: \Sigma \times \mathcal{A} \to \mathcal{R}$
mapping calls to results. A \emph{direct connection} between client
and server produces:
\[
  \mathrm{direct}(c) = \mathcal{S}(c.\text{name},\,c.\text{args})
  \quad\text{for a call } c = (\text{name}, \text{args}).
\]

\begin{definition}[Tool Call Trace]
\label{def:trace}
A \emph{tool call trace} $\tau = (c_1, r_1, \ldots, c_n, r_n)$ is
an alternating sequence of calls $c_i \in \Sigma \times \mathcal{A}$
and results $r_i \in \mathcal{R}$, produced in session order.
The \emph{result trace} of $\tau$ is $\rho(\tau) = (r_1, \ldots, r_n)$.
\end{definition}

\subsection{MCP Governance Proxy}
\label{sec:proxy}

\begin{definition}[Proxy Session State]
\label{def:proxy-state}
A \emph{proxy session state} $s \in \ProxyState$ is a tuple
\[
  s = (\tau,\; \Azero,\; \Dhat_\text{ema},\; \mathcal{E}_\text{pend})
\]
where $\tau$ is the current trace (\ref{def:trace}), $\Azero$ is the
admission snapshot (fixed at session initialisation), $\Dhat_\text{ema}$
is the EMA-smoothed drift estimate, and $\mathcal{E}_\text{pend}$ is
the map of pending evidence blocks awaiting APB responses (evidence\,id
$\to$ $\Es$). The initial state $s_0 = (\varepsilon,\,\Azero^{(0)},\,
0,\,\emptyset)$.
\end{definition}

\begin{definition}[Governance Decision Function]
\label{def:govern}
The \emph{governance decision function}
$\mathrm{govern}: \ProxyState \times \Sigma \times \mathcal{A}
\to \{\ADMIT,\;\HALT,\;\DENY\}$
is:
\begin{align*}
  s' &= \mathrm{update}(s,\,\text{name},\,\text{args})
         \quad\text{(append to } s.\tau\text{, recompute }\Dhat\text{)}\\
  d_\text{RAM} &= \mathrm{RAMGate}(\text{name},\;\text{RS}(\text{name}),\;s'.\Dhat_\text{ema})\\
  d &=
    \begin{cases}
      \ADMIT  & \text{if } d_\text{RAM} = \ADMIT\\
      \DENY   & \text{if } d_\text{RAM} = \DENY\\
      \mathrm{RecoveryLoop}(d_\text{RAM},\;s'.\Dhat_\text{ema},\;\ldots)
              & \text{if } d_\text{RAM} = \HALT
    \end{cases}
\end{align*}
where $\mathrm{RS}: \Sigma \to [0,100]$ is the risk score mapping.
\end{definition}

\begin{definition}[MCP Governance Proxy]
\label{def:proxy}
An \emph{MCP Governance Proxy} $\Proxy$ for principal set $\Pset$ is
a stateful function:
\[
  \Proxy: \ProxyState \times \Sigma \times \mathcal{A}
        \;\to\;
        \mathcal{R} \;\cup\; \{p9/\mathrm{apbRequired}(\Es,\,\text{eid})\}
                   \;\cup\; \{\mathrm{GOVERNANCE\_DENY}\}
\]
On receiving call $c = (\text{name}, \text{args})$ in state $s$:
\begin{enumerate}[leftmargin=2em, topsep=2pt, itemsep=1pt]
  \item Compute $d = \mathrm{govern}(s,\,\text{name},\,\text{args})$.
  \item If $d = \ADMIT$: forward $c$ to server, return
        $r = \mathcal{S}(\text{name}, \text{args})$,
        update $s$.
  \item If $d \in \{\HALT,\,\texttt{ESCALATE}\}$: construct
        $\Es = \mathrm{construct\_evidence}(s',\,\text{cause})$,
        assign $\text{eid} \gets \mathrm{fresh\_id}()$,
        record $s'.\mathcal{E}_\text{pend}[\text{eid}] \gets \Es$
        (with $\ahash$ set to the hash of the halted call),
        signal the halt to the client as $p9/\mathrm{apbRequired}(\Es,\,\text{eid})$.
        \emph{The wire form of this signal is specified here but not
        implemented}: see \S\ref{sec:impl}.
  \item If $d = \DENY$: return $\mathrm{GOVERNANCE\_DENY}$.
\end{enumerate}
On receiving $p9/\mathrm{apbResponse}(\text{eid},\,\APB)$:
\begin{enumerate}[leftmargin=2em, topsep=2pt, itemsep=1pt]
  \item Retrieve $E_{s,\mathrm{exp}} = s.\mathcal{E}_\text{pend}[\text{eid}]$.
  \item Verify $\APB.\Es = E_{s,\mathrm{exp}}$ and $\mathrm{verify}(\APB, \Pset)$.
  \item If valid: remove from pending, execute $\APB.\Dh.\text{decision}$;
        a $\RESUME$ is applied only to the call whose hash equals
        $\APB.\Es.\ahash$ (the reference client refuses to execute any other).
  \item If invalid: emit $p9/\mathrm{apbRejected}(\text{eid},\,\text{reason})$.
\end{enumerate}
\end{definition}

\paragraph{Protocol extension (specified, not implemented on the wire).}
The three custom message types $p9/\mathrm{apbRequired}$,
$p9/\mathrm{apbResponse}$, and $p9/\mathrm{apbRejected}$ are specified
as JSON-RPC notifications over the MCP transport
(\texttt{proxy/protocol\_extension.py} defines their serialisation).
\emph{The reference implementation does not send them as notifications.}
It encodes the halt in the \emph{result} of the tool call
(Remark~\ref{rem:backward}).

\begin{remark}[Behaviour Under Legacy Clients]
\label{rem:backward}
In the reference implementation a halted call is \emph{not} forwarded to
the server; the proxy returns a text result
(\texttt{[GOVERNANCE\_HALT] evidence\_id=\ldots}). A standard MCP client
therefore sees the call \emph{complete} with that text. The governed
tool is not executed, so no unauthorised execution occurs; but the
client is not blocked or timed out as an earlier version of this paper
claimed, and the agent may read the text, retry (each retry is governed
again and may create a further pending halt) or continue without the
action. Whether the agent surfaces the halt to a human then depends on
the agent, not on the proxy. A wire-level $p9/\mathrm{apbRequired}$ that
blocks the call until a response or timeout is the intended design and
is future work.
\end{remark}

\subsection{Multi-Hop Authority Delegation (A2A)}
\label{sec:a2a}

In Agent-to-Agent delegation, an originating agent $A_1$ delegates
a task to a sub-agent $A_2$ (possibly recursively). The sub-agent
makes tool calls to a server; the proxy governs those tool calls.

\begin{definition}[Delegation Chain]
\label{def:delegation-chain}
A \emph{delegation chain} of depth $n$ is a sequence
$\chain = (A_1, A_2, \ldots, A_n)$ where $A_1$ is the
\emph{originating agent}, each $A_i \delegateto A_{i+1}$ is
a delegation event recorded in the IML trace, and $A_n$ makes
the proxied tool call. The originator $\orig(\chain) = A_1$.
\end{definition}

\begin{definition}[Multi-Hop APB Semantics]
\label{def:mhapb}
For a governance event triggered by $A_n$'s tool call in chain
$\chain = (A_1, \ldots, A_n)$, the required APB has:
\begin{align*}
  \Es.\text{cause} &\supseteq \{
    \texttt{delegation\_chain} = \mathrm{id}(\chain),\;
    \texttt{originator} = \mathrm{id}(A_1)
  \}\\
  \Dh.\Hi &\in \Pset_{\orig(\chain)}
\end{align*}
where $\Pset_{\orig(\chain)}$ is the principal set registered for the
originating agent $A_1$.
\end{definition}

The semantics formalise the accountability principle: the human
accountable for the originating agent's actions is the one who must
authorise a recovery from any governance event caused by agents
operating under that agent's authority.

\section{Theorems}
\label{sec:theorems}

\subsection{T9.1\,---\,Transparency on the Non-Halt Path}
\label{sec:t91}

\begin{remark}[Status of T9.1]
T9.1 holds \emph{by construction}: it restates step~2 of
Definition~\ref{def:proxy}. Its content is the design commitment that
the proxy never alters an admitted call or its result. It makes three
restrictions explicit. (i)~$\mathcal{S}$ is a function of the call alone;
for a stateful or non-deterministic server the statement applies to
\emph{identical server behaviour} on the forwarded calls, and calls that
are halted are \emph{not} forwarded, so the server's state can then
differ from a direct connection's. (ii)~The hypothesis ($\ADMIT$ for
every call) excludes the halt path, which is where a client unaware of
P9 is affected (Remark~\ref{rem:backward}). (iii)~The experiments do not
test T9.1: the latency gate of E1 is a performance threshold, and E2
checks only that every halt ends in an APB.
\end{remark}

\begin{theorem}[Transparency on the Non-Halt Path]
\label{thm:transparency}
Let $\tau = (c_1, \ldots, c_n)$ be a sequence of tool calls processed
by proxy $\Proxy$ in session state $s_0$, such that
$\mathrm{govern}(s_i,\,c_{i+1}) = \ADMIT$ for all $i \in \{0,\ldots,n-1\}$.
Then the result trace returned to the client is equal to the result
trace produced by a direct connection to the server:
\[
  \rho(\tau_\Proxy) = \rho(\tau_\text{direct}).
\]
\end{theorem}

\begin{proof}
Each step is independent of the others, so the argument is the same for
every $n$ (no induction hypothesis is needed); we give the case $n=1$
and the general step.

\emph{Base case} ($n=1$).
Call $c_1 = (\text{name}, \text{args})$ with $d_1 = \ADMIT$.
By Definition~\ref{def:proxy} step~2, $\Proxy$ forwards $c_1$ to the
server and returns $r_1 = \mathcal{S}(\text{name}, \text{args})$
unchanged. By definition of direct connection,
$\mathrm{direct}(c_1) = \mathcal{S}(\text{name}, \text{args}) = r_1$.
Therefore $\rho(\tau_\Proxy) = (r_1) = \rho(\tau_\text{direct})$.

\emph{Inductive step}.
Assume the claim holds for all sequences of length $n-1$.
Consider $c_n$ with $d_n = \ADMIT$.
By the inductive hypothesis, $(r_1, \ldots, r_{n-1})$ is identical
under $\Proxy$ and direct connection.
For call $c_n$: by Definition~\ref{def:proxy} step~2,
$\Proxy$ forwards $c_n$ to the server and returns
$r_n = \mathcal{S}(c_n.\text{name}, c_n.\text{args})$ unchanged,
regardless of the internal proxy state $s_n$ (the state affects only
the governance decision, which is $\ADMIT$ by hypothesis, not the
forwarded call or response).
By Lemma~\ref{lem:l911}, the result is identical to $\mathrm{direct}(c_n)$.
Therefore $\rho(\tau_\Proxy) = (r_1, \ldots, r_n) = \rho(\tau_\text{direct})$.
\end{proof}

\begin{lemma}[MCP Response Identity Under Passthrough]
\label{lem:l911}
For any tool call $c = (\text{name}, \text{args})$ and proxy state $s$,
if $\mathrm{govern}(s,\,c) = \ADMIT$, then
$\Proxy(s,\,c).\text{result} = \mathcal{S}(\text{name},\,\text{args})$.
\end{lemma}

\begin{proof}
By Definition~\ref{def:proxy} step~2: on $d = \ADMIT$, the proxy
forwards the unmodified call $(\text{name}, \text{args})$ to the
server and returns the server's unmodified response.
No transformation is applied to either the call arguments or the result.
\end{proof}

\begin{remark}[Non-halt path observational equivalence]
Theorem~T9.1 makes precise the claim that governance is \emph{transparent}
to non-P9-aware clients. The proxy introduces latency on the non-halt
path (bounded in T9.2) but produces no semantic difference in the
tool-call results.
\end{remark}

\subsection{T9.2\,---\,Halt Latency Decomposition}
\label{sec:t92}

\begin{remark}[Status of T9.2]
T9.2 is a \emph{decomposition}: the total is the sum of the three terms
it defines, and it gives no bound on $\Dpolicy$. That term depends on
the drift monitor (the default EMA monitor recomputes over the trace,
$O(|\tau|)$; the windowed monitor is $O(\text{window})$) and the RAM
Gate and Recovery Loop draw pseudo-random numbers, so $\Dpolicy$ is
random and is characterised only empirically (E1). The time to
\emph{validate} an APB runs after the human's answer, so it is not part
of the time to reach the halt. We keep the statement for the structure it
shows, not as a guarantee.
\end{remark}

\begin{theorem}[Halt Latency Decomposition]
\label{thm:latency}
Let $c$ be a tool call that triggers a governance event at the proxy
at time $t_0$. The agent receives the halt signal (in the reference
implementation, as the tool result; see Remark~\ref{rem:backward}) no later than
\[
  t_0 + \Dpolicy + \Dnet,
\]
and APB validation upon the client's response completes within an
additional $\Dverify$, so the total governance resolution latency is
bounded by
\[
  \Delta_\text{halt} \;\leq\; \Dnet + \Dverify + \Dpolicy.
\]
\end{theorem}

\begin{proof}
By construction of Definition~\ref{def:proxy} and the governance stack.

\emph{Governance evaluation.}
On receiving $c$ at $t_0$, the proxy runs $\mathrm{govern}(s, c)$:
(i)~The IML trace update is $O(|\tau|)$, bounded by the session trace
length; we write this cost as $\Dpolicy^{(1)}$.
(ii)~The RAM Gate executes a constant number of pseudo-random draws
for each of $|\{I,B,R,C,E\}| = 5$ components; time is $O(1)$, included
in $\Dpolicy$.
(iii)~The Recovery Loop executes at most $k_\text{max}$ iterations
(a compile-time constant), each $O(1)$; total $O(k_\text{max})
\subseteq \Dpolicy$.
The governance evaluation completes at $t_0 + \Dpolicy$.

\emph{Signal delivery.}
The proxy emits $p9/\mathrm{apbRequired}$ immediately after the
governance evaluation (Definition~\ref{def:proxy} step~3).
The message travels from proxy to client in network time $\Dnet$.
The client receives the halt signal at $t_0 + \Dpolicy + \Dnet$.

\emph{APB validation.}
When the client responds with $p9/\mathrm{apbResponse}$, the proxy
verifies the APB. By Lemma~\ref{lem:l921}, verification is $O(1)$,
denoted $\Dverify$.

\emph{Total.}
Summing: $\Delta_\text{halt} = \Dpolicy + \Dnet + \Dverify$.
Rewriting in the bound's conventional order:
$\Delta_\text{halt} \leq \Dnet + \Dverify + \Dpolicy$.
\end{proof}

\begin{lemma}[Verification Time is $O(1)$]
\label{lem:l921}
APB verification (predicates V1--V5) terminates in $O(1)$ time.
\end{lemma}

\begin{proof}
V1: ed25519 signature verification is a fixed number of field
operations on curve25519 regardless of message length (the message
is pre-hashed internally); $O(1)$.
V2: registry lookup by key in a hash map; $O(1)$.
V3: ISO 8601 timestamp comparison; $O(1)$.
V4: age computation (two timestamp subtractions); $O(1)$.
V5: hash-map lookup for event\_id in the seen-events set; $O(1)$ amortised.
The sum of five $O(1)$ operations is $O(1)$.
\end{proof}

\begin{remark}[Practical magnitude of the bound]
Experiment~E1 (\S\ref{sec:exp1}) measures the windowed ADMIT path at
mean $46.5\,\si{\micro\second}$ and the HALT path at mean
$57.0\,\si{\micro\second}$, so $\Dpolicy + \Dverify \approx 57\,\si{\micro\second}$.
E1 calls the interceptor as a Python function, so it measures the
\emph{decision} cost and not stdio/JSON-RPC serialisation, process
switches or the network; with $\Dnet$ absent the figure is
$\Delta_\text{halt} \approx 57\,\si{\micro\second}$. If one
\emph{assumes} a LAN term $\Dnet \approx 5\,\si{\milli\second}$ (not measured here),
the sum would be $\approx 5.06\,\si{\milli\second}$, small against LLM
inference latencies ($\approx 100\,\si{\milli\second}$ to $\approx 25\,\si{\second}$).
A real transport measurement is future work.
\end{remark}

\subsection{T9.3\,---\,Multi-Hop Authority Propagation}
\label{sec:t93}

\begin{remark}[What T9.3 does and does not establish]
The attribution of accountability to the originator is an
\emph{assumption of the model}, not something derived from the series'
earlier results. The first release justified it with DC.1 (immutability
of the baseline), which is unrelated to who is accountable. We now state
it as an axiom and prove the rest from it.
\end{remark}

\begin{description}[leftmargin=2em, topsep=2pt]
  \item[AX9.1 (Attribution to the originator).]
        The principal accountable for a governance event raised by
        $A_n$ in chain $\chain$ is a principal registered for
        $A_1 = \orig(\chain)$; sub-agents $A_i$ ($i>1$) are not
        principals in their own right.
  \item[AX9.2 (Trusted chain record).]
        The delegation events in the trace are written by a component
        the adversary cannot influence.
\end{description}

\begin{theorem}[Multi-Hop Authority Propagation, under AX9.1--AX9.2]
\label{thm:multihop}
Let $\chain = (A_1, A_2, \ldots, A_n)$ be a delegation chain and
$c$ a tool call by $A_n$ that triggers a governance event at
the proxy governing $A_n$'s tool calls. Then:
\begin{enumerate}[leftmargin=2em, topsep=2pt, itemsep=1pt]
  \item[(a)] The delegation chain $\chain$ is uniquely and canonically
        determined by the IML trace at time $t_e$
        (Lemma~\ref{lem:l931}).
  \item[(b)] The originating agent $A_1 = \orig(\chain)$ is
        well-defined.
  \item[(c)] The required APB's $\Dh.\Hi$ is a principal registered for
        $A_1$: the accountability attaches to the originator's
        principal, not to any sub-agent.
  \item[(d)] For the degenerate chain $n=1$ (no delegation),
        the theorem reduces to P8's T8.2 (Non-Repudiability) with
        $A_1$'s principal.
\end{enumerate}
\end{theorem}

\begin{proof}
We prove the four parts by case analysis on chain depth $n$. The
argument for $n>1$ is direct; nothing is carried over from depth $n-1$.

\emph{Case $n = 1$ (degenerate, no delegation).}
$\chain = (A_1)$, $\orig(\chain) = A_1$.
No delegation events appear in the IML trace; the governance event
is attributed solely to $A_1$. The required APB is the standard P8
APB with $\Dh.\Hi \in \Pset_{A_1}$ (the principal set of $A_1$).
This is exactly T8.2 of P8 \citep{fernandez2026ibg}, establishing (d).
Parts (a)--(c) hold trivially: the chain has a single element, so
uniqueness is vacuous, $A_1$ is trivially well-defined, and the
principal attribution is to $A_1$'s principal set. \checkmark

\emph{Case $n > 1$ (delegation present).}
Consider chain $\chain = (A_1, A_2, \ldots, A_n)$.

(a) \emph{Canonicality of $\chain$} (using AX9.2).
By Lemma~\ref{lem:l931}, the delegation chain is determined by the
IML trace prefix $\tau_{\le t_e}$. Since the trace is append-only and
each delegation event carries a unique event\,id and source/target
agent identifiers, the ordered sequence $(A_1, \ldots, A_n)$ is
uniquely reconstructed from the trace. \checkmark

(b) \emph{Well-definedness of $\orig(\chain)$}.
$\orig(\chain) = A_1$ is the agent from which no prior delegation
event appears in $\tau_{\le t_e}$: there exists no $A_0$ such
that $A_0 \delegateto A_1$ appears in the trace.
By (a), this agent is unique. \checkmark

(c) \emph{Principal accountability.}
By AX9.1, the principal accountable for a governance event raised by
$A_n$ is registered for $A_1$. The proxy therefore requires
$\Dh.\Hi \in \Pset_{A_1}$ (this is Definition~\ref{def:mhapb}; the
reference implementation enforces it with the
\texttt{allowed\_H\_ids} check, \S\ref{sec:exp3}). This is a
consequence of the axiom, not an independent derivation: the theorem
records that the rule is well-defined and recorded in $\Es$, and
\emph{not} that it is the right accountability rule. \checkmark
\end{proof}

\begin{remark}[Limits of T9.3]
(i)~The chain is \emph{unauthenticated}: no delegator signs the
delegation, and in the reference implementation the chain is a
configuration parameter of the interceptor, so E3 checks that a
configured value is copied into $\Es$. A malicious sub-agent that
declares a false chain can divert accountability to another principal;
authenticated delegation (a signature by each delegator over the next
hop, as in capability or credential chaining) is future work. (ii)~Only
linear chains are covered: branching (A1 delegating to A2 and A3),
cycles and re-delegation with reduced scope are not modelled.
(iii)~Depth $>2$ in E3 uses synthetic chains.
\end{remark}

\begin{lemma}[Delegation Chain Canonicalization]
\label{lem:l931}
The delegation chain $\chain$ is deterministic given the IML trace
prefix $\tau_{\le t_e}$.
\end{lemma}

\begin{proof}
Each delegation event $A_i \delegateto A_{i+1}$ appends a record
$(\text{agent}=A_i,\,\text{action}=\texttt{delegation},\,
\text{target}=A_{i+1},\,\text{event\_id}=\text{uid}_k)$
to the trace. Since the trace is strictly append-only (no deletions,
no reordering), the sequence of delegation events in $\tau_{\le t_e}$
is uniquely ordered by their position in the trace.
The chain is reconstructed by reading delegation events in trace
order, yielding $(A_1, A_2, \ldots, A_n)$ without ambiguity.
\end{proof}

\begin{remark}[Limitation: A2A specification maturity]
The A2A protocol \citep{google2025a2a} is at draft stage at the time
of writing. Our implementation (\S\ref{sec:impl}) uses a simulated
A2A setup; the formal definitions above are stated for the general
case. We note that the formal result (T9.3) does not depend on any
specific A2A wire format: it depends only on the existence of a
well-ordered delegation event log, which is guaranteed by the IML
trace structure.
\end{remark}

\section{Implementation}
\label{sec:impl}

\subsection{Architecture}

The implementation is available at
\url{https://github.com/chelof100/mcp-governed-agents}.
It consists of four layers:

\begin{description}[leftmargin=2em, topsep=4pt]
  \item[Frozen baseline (P7+P8).]
        Modules \texttt{agent/}, \texttt{stack/}, \texttt{iml/},
        and \texttt{baselines/} are copied verbatim from P8's
        repository. One change: \texttt{stack/apb.py} gains the optional
        field $\ahash$ of $\Es$ (absent $\Rightarrow$ omitted from the
        canonical form, so P8 APBs are unchanged). All 61 P8 tests pass.
  \item[Proxy layer (P9 new).]
        \texttt{proxy/mcp\_interceptor.py}: the \texttt{MCPInterceptor}
        class, one instance per session, runs IML\,$\to$\,RAM\,$\to$\,
        Recovery Loop per tool call and returns $(\text{decision},
        \text{payload})$.
  \item[Protocol extension.]
        \texttt{proxy/protocol\_extension.py}: dataclasses for
        $p9/\mathrm{apbRequired}$, $p9/\mathrm{apbResponse}$, and
        $p9/\mathrm{apbRejected}$ with JSON-RPC serialisation (used by the
        in-process driver; not sent over a transport).
  \item[Server entry point.]
        \texttt{proxy/governed\_server.py}: \texttt{GoverningProxy}
        wraps an MCP server via FastMCP, connecting as a client to the
        real server (stdio subprocess) while serving the upstream client
        on its own stdio. It hard-codes the five tools of the toy
        server and encodes a halt as a text result
        (Remark~\ref{rem:backward}). \emph{No test and no experiment
        exercises it}: all experiments call the interceptor directly.
\end{description}

\subsection{Usage Example}

Inserting the proxy into an existing deployment requires two lines
of configuration: create an \texttt{MCPInterceptor} for the session
and pass it to the client driver.

\begin{verbatim}
from proxy.mcp_interceptor import MCPInterceptor
from client.mcp_agent_client import MCPAgentClient
from agent.principal import PrincipalRegistry, generate_keypair

# One-time setup: register human principal
sk, pk = generate_keypair()
registry = PrincipalRegistry(); registry.add(Principal("human-H", pk))

# Per-session: proxy + client
interceptor = MCPInterceptor(registry=registry, H_id="human-H")
client = MCPAgentClient(interceptor=interceptor,
                        sk_bytes=sk, H_id="human-H",
                        auto_decision="RESUME")

# Agent calls tools transparently; governance is enforced by the proxy
result = client.call_tool("write_data", {"target": "db", "payload": "x"})
\end{verbatim}

\noindent
No changes to the tool server or the tool-calling logic are required.
For A2A delegation, pass \texttt{agent\_id} and \texttt{delegation\_chain}
to \texttt{MCPInterceptor}; the originator is automatically recorded
in every \texttt{APBRequired} evidence block.

\section{Experiment~E1: Latency Overhead}
\label{sec:exp1}

\subsection{Setup}

We measure the latency overhead introduced by the governance proxy
relative to a passthrough proxy.

\textbf{Server:} \texttt{proxy/toy\_server.py}, five deterministic tools.
\textbf{Client:} \texttt{experiments/exp\_e1\_overhead.py}.
\textbf{Conditions:}
(a)~\emph{Passthrough} --- unmodified forwarding baseline;
(b)~\emph{Governed ADMIT (O($n$) accumulating)} --- full IML over growing trace, session window reset each call;
(c)~\emph{Governed ADMIT (O(1) windowed)} --- \texttt{WindowedIMLMonitor}, $W{=}100$, no session reset, flat overhead across arbitrary session length;
(d)~\emph{Governed HALT} --- full pipeline including APB construction and ed25519 verification.
Calls per condition: $10{,}000$ (ADMIT), $1{,}000$ (HALT).
\textbf{Hardware:} Intel Core i9-13900HX, 32\,GB RAM, $\Dnet = 0$ (local in-process).

\subsection{Results}

\input{../results/exp_e1/exp_e1_table.tex}

\noindent
Table~\ref{tab:e1-overhead} reports all four conditions.
The \emph{windowed} O(1) monitor achieves P95\,=\,$51.8\,\si{\micro\second}$
on an indefinite-length session, below the (arbitrary) latency threshold of
$10\,\si{\milli\second}$ that we use as a gate; this is a performance gate and
says nothing about T9.1. The HALT condition adds only
$\approx 10\,\si{\micro\second}$ over the ADMIT baseline
($57.0\,\si{\micro\second}$ vs.\ $46.5\,\si{\micro\second}$ mean), consistent
with the decomposition of T9.2. One machine, one run per condition, no
confidence intervals; the windowed condition has outliers (maximum
$21.4\,\si{\milli\second}$) that the P95 hides.

\subsection{Discussion}

The passthrough baseline ($0.1\,\si{\micro\second}$ mean) isolates the pure
dispatch overhead; the governance stack adds $\approx 46\,\si{\micro\second}$
per call in the windowed configuration.
This cost is orders of magnitude below typical local LLM inference
latencies, confirming that governance at the MCP layer is not a
practical bottleneck.

The O($n$) accumulating monitor (\texttt{IMLMonitor}) achieves slightly
lower P50 at short session lengths (36.7\,\si{\micro\second} vs.\
42.5\,\si{\micro\second}) because it avoids the deque-update bookkeeping.
However, its overhead grows with session length: at $n=1{,}000$ events it
reaches $\approx 203\,\si{\micro\second}$ mean, and extrapolates to
$\approx 2\,\si{\milli\second}$ at $n=10{,}000$.
The windowed monitor (O(1) per call, window $W=100$) bounds overhead
regardless of session length, which is the correct choice for
long-running production deployments.

The \texttt{IMLMonitor.compute()} growth profile (measured at
$n \in \{1, 50, 100, 200, 500, 1000, 2000\}$) confirms linear growth.
We adopt the \texttt{WindowedIMLMonitor} as the default in all subsequent
experiments.

\subsection{Setup}

We exercise the APB pipeline through the interceptor, covering the

\textbf{Governance outcome taxonomy used here:}

\subsection{Results}

\input{../results/exp_e2/exp_e2_table.tex}

\noindent
Across $1{,}000$ total steps (E2.A), the proxy issued $310$ HALT events

The 310:21 ratio of HALT to DENY demonstrates that the two paths
are clearly distinguishable and correctly reported.

\section{Experiment~E3: Multi-Hop A2A}
\label{sec:exp3}

\subsection{Setup}

We validate T9.3 empirically through three sub-experiments under
controlled multi-hop simulation aligned with current A2A draft
semantics \citep{google2025a2a}. All delegation chains are
instantiated within a single process using the proxy's
\texttt{delegation\_chain} and \texttt{agent\_id} parameters;
cross-vendor interoperability with live, heterogeneous A2A
ecosystems is not claimed---the results establish formal and
implementation feasibility pending ecosystem-wide protocol
stabilisation.

\emph{E3.A}: $10$ independent depth-1 chains ($A \to B$), $30$ steps each.
\emph{E3.B}: $1$ depth-2 chain ($A \to B \to C$), $30$ steps each.
\emph{E3.C}: Depth invariance scaling, depths $1$--$5$, $5$ runs per depth,
$30$ steps per run.

Each run verifies: (i)~the \texttt{delegation\_chain} field in the
APBRequired matches the configured chain, (ii)~$\texttt{originator} = A_1$
(chain[0]) regardless of chain depth, and (iii)~all APBs pass V1--V5.

\subsection{Results}

\input{../results/exp_e3/exp_e3_table.tex}

\noindent
E3.A and E3.B (Table~\ref{tab:e3-a2a}) demonstrate correct originator binding and delegation-chain recording at depths 1 and 2.
E3.C (Table~\ref{tab:e3c-depth}) extends validation to depths 1--5:
across $334$ total HALT events ($65$--$69$ per depth),
the originator is $A_1 =$ chain[0] in $100\%$ of cases at every depth.

\subsection{Discussion}

\section{Experiment~E4: Concurrency Stress}
\label{sec:exp4}

\subsection{Setup}

We test the proxy under concurrent client load to verify that
governance does not introduce race conditions or session-state crosstalk.

\textbf{Two modes:}
\emph{Thread mode} (\texttt{ThreadPoolExecutor}): GIL-limited; $N \in \{1,4,16,64\}$
concurrent sessions, $10$ sessions per level, $60$ steps each.
\emph{Process mode} (\texttt{multiprocessing.Pool}): true parallel (no GIL);
$N \in \{1,4,8,16\}$, $12$ sessions per level, $200$ steps each.
The process-mode upper limit is capped at $N{=}16$ due to the Windows
\texttt{WaitForMultipleObjects} handle limit (max 63 handles; $N{=}64$
would require 66 handles and raises a \texttt{ValueError}).

\subsection{Results}

\input{../results/exp_e4/exp_e4_table.tex}

\noindent
Thread mode (Table~\ref{tab:e4-concurrency}): $0$ exceptions at all $N$,
$100\%$ APB validity.
Throughput saturates at $\approx 2{,}800$ calls/s for $N \ge 4$,
yielding $\approx 2\%$ scaling efficiency at $N{=}64$ (GIL-limited, as expected:
the IML drift computation via scipy JSD is CPU-bound).
Process mode: $0$ exceptions up to $N{=}16$, $100\%$ APB validity.
Throughput peaks at $N{=}4$ ($1{,}146$ calls/s) before declining for $N{=}8$
and $N{=}16$ due to IPC and serialisation overhead dominating for the
short sessions ($200$ steps per session).

\subsection{Discussion}

No exceptions and no APB-validity failures occur at any concurrency
level or mode. This is a consequence of the design rather than a
finding: each \texttt{MCPInterceptor} instance is independent, so
concurrent sessions share no drift state or pending APBs. The
interesting case, many sessions contending for a \emph{shared} registry
or log, is not tested.

The sub-linear thread scaling is expected: the proxy's governance
computation (IML JSD + RAM pseudo-random draws) is CPU-bound Python,
and the GIL serialises CPU work across threads.
For I/O-bound agents (where LLM inference dominates) this is not a
bottleneck: the $\approx 2{,}800$ calls/s thread throughput exceeds the
tool-call rate of any realistic LLM agent by two to three orders of magnitude.

The process-mode throughput is lower than thread mode's. We attribute
this to the pickle-serialised worker pool on Windows, and we
\emph{conjecture} that with \texttt{fork} on Linux the overhead
disappears and the mode scales close to linearly; we have not measured
it on Linux.

\section{Experiment~E5: Adversarial Regression Suite}
\label{sec:exp5}

\subsection{Setup}

We test six attack scenarios targeting the governance proxy's APB
verification pipeline.
Each attack attempts to bypass the governance halt or inject an
unauthorized resume decision.
The proxy must reject all six with a specific, distinguishable error
message. The attacks were written by the author, each against the
predicate the design already expects; the suite is a regression test of
those defences. It contains no adaptive attacker, no fuzzing and no model
of an adversary's capabilities, so it is not evidence that the proxy is
secure.

\begin{description}[leftmargin=2em, topsep=2pt, itemsep=2pt]
  \item[A1 (Wrong-key signing).]
        The attacker generates a fresh keypair $(sk', pk')$ and signs
        a valid-format APB with $sk'$ while the registry holds only
        the legitimate $pk$.
        Expected rejection: V1 (INVALID\_SIGNATURE).
  \item[A2 (Evidence tampering).]
        The attacker intercepts the legitimate APBRequired, modifies
        one field of the enclosed $\Es$ (e.g., flips a byte in
        $\hat{D}$), and re-signs with their key.
        Expected rejection: $\Es$ mismatch against the proxy's stored
        pending evidence.
  \item[A3 (APB replay).]
        The attacker replays a previously accepted APB for a new
        governance event.
        Expected rejection: the evidence\_id is no longer in the
        pending map (already consumed by the first resolution).
  \item[A4 (Revoked-principal authorization).]
        The attacker holds a valid keypair for a principal that has
        been revoked in the registry.
        Expected rejection: V3 (PRINCIPAL\_REVOKED / principal not
        active at $t_e$).
  \item[A5 (Authority substitution in A2A delegation).]
        In a two-agent chain ($A_A \to A_B$), the interceptor is
        configured with $\texttt{allowed\_H\_ids} = \{H_A\}$
        (only the originator's principal may authorize).
        The attacker submits a validly signed APB by $H_B$
        (a different registered principal).
        Expected rejection: authority confinement violation (the
        \texttt{allowed\_H\_ids} check).
  \item[A6 (Cross-call APB).]
        Two calls are pending. The APB the principal signed for call~$Y$
        is presented against the evidence\_id of call~$X$. Both are
        legitimate and validly signed; only the call differs.
        Expected rejection: $\Es$ mismatch (the two blocks differ in
        \texttt{event\_id} and in $\ahash$), with $Y$'s pending halt left
        untouched.
\end{description}

\subsection{Results}

\input{../results/exp_e5/exp_e5_table.tex}

\noindent
All six attacks are rejected (Table~\ref{tab:e5-adversarial}), each with
the distinguishing message the design predicts.

\subsection{Discussion}

\paragraph{A1 (Wrong-key).}
ed25519 signature verification is unconditional: the signature either
validates under the registered public key or it does not.
The proxy never falls back to an alternate key.

\paragraph{A2 (Evidence tampering).}
The proxy stores the canonical $\Es$ at the moment it emits APBRequired
and compares it field-by-field against the $\Es$ embedded in the APB response.
The comparison is prior to V1 signature verification; even a correctly
re-signed tampered APB is rejected at this step.

\paragraph{A3 (Replay).}
Each evidence\_id is consumed on first acceptance and deleted from the
pending map.
Replaying a used evidence\_id against an empty pending slot returns
``unknown evidence\_id''. In this suite the rejection therefore comes
from the pending map, \emph{not} from V5. The first release stated that
V5 was applied but called the verifier without a seen-event set, so V5
never ran; it now does (a unit test covers it). The seen-event set lives in
memory and is lost when the interceptor restarts, as does the pending
map, so neither survives a restart.

\paragraph{A4 (Revoked principal).}
The registry marks revoked principals with an \texttt{is\_active=False}
flag; V3 checks this flag at the $t_e$ timestamp.
Revocation is permanent and non-reversible in the current implementation,
consistent with P8 §5.3.

\paragraph{A5 (Authority confinement).}
The \texttt{allowed\_H\_ids} mechanism enforces that only
the originator's registered human principal may authorize governance
events in a delegation chain.
This prevents a sub-agent's principal from usurping governance authority
even if their key is legitimately registered elsewhere.
This is the only attack vector that goes beyond the P8 V1--V5 predicates;
it is specific to the multi-hop A2A context.

\section{Discussion}
\label{sec:discussion}

\subsection{Security Analysis}
\label{sec:security}

Experiment E5 validates the proxy against five concrete attacks.
We summarise the security properties and their correspondence to the
formal guarantees.

\paragraph{Signature unforgeability (T8.2, V1).}
An attacker without access to the registered principal's $sk_i$ cannot
produce a valid APB for any governance event.
This follows from the standard unforgeability of ed25519 under the
discrete-log assumption on curve25519.
E5-A1 confirms this empirically: a fresh keypair produces a signature
that V1 rejects.

\paragraph{Evidence integrity (proxy-enforced).}
The proxy's own pending-evidence map is the reference for $\Es$ comparison.
Even if an attacker re-signs a modified $\Es$ with a legitimately obtained
key, the proxy detects the mismatch before invoking the verifier.
E5-A2 confirms this: evidence tampering is caught independently of
signature validity.

\paragraph{Replay resistance (V5).}
Each APB is tied to a single governance event via the evidence\_id,
which is consumed on first resolution.
An attacker cannot re-use a past APB to resolve a new governance event.
E5-A3 confirms this: replayed evidence\_ids are rejected with
``unknown evidence\_id''.

\paragraph{Principal lifecycle enforcement (V3).}
Revocation of a principal is immediate and permanent.
Any APB signed by a revoked principal is rejected at V3.
E5-A4 confirms this.

\paragraph{Authority confinement under A2A delegation.}
In a delegation chain, the \texttt{allowed\_H\_ids} set restricts which
human principals may authorise governance events.
This prevents lateral authority injection: a principal registered for a
sub-agent cannot usurp the originator's governance authority.
E5-A5 confirms this.

\paragraph{Remaining attack surface.}
The adversaries M1--M7 of \S\ref{sec:threats} are not covered by E5.
M1 and M2 need infrastructure-level mitigations (code signing,
attestation, audit logs); the others are open.

\subsection{Production Deployment}

By design the proxy can be inserted into an MCP deployment topology
without modifying the agent client or the tool server; this has not
been demonstrated against a third-party client or server, and it
presupposes that the proxy is the only path to the server (M3).
Candidate insertion points are: between the agent and its tool server
in a single-host deployment; or at the network boundary (reverse
proxy) in a cloud deployment. In the latter case, the proxy runs as
a sidecar service, and $\Dnet$ reflects a real network hop.

\paragraph{Key store placement.}
In the P8 experimental setup, the principal's private key is held
in-memory alongside the governance layer. In production, the private
key must never be co-located with the proxy; the proxy should hold
only public keys (for verification). The principal signs $\Dh$ on
their own device and returns the signed APB via $p9/\mathrm{apbResponse}$.
This separation is the deployment requirement enforced by T8.3:
without the private key, the proxy cannot forge a valid APB.

\subsection{Threat Model Under Proxy Deployment}
\label{sec:threats}

Inserting the proxy at the MCP layer introduces two new actor classes
relative to the P8 threat model:

\begin{description}[leftmargin=2em, topsep=2pt]
  \item[M1. Compromised proxy process.]
        The proxy is a process with access to the MCP stream and the
        per-session governance state. It does not hold any principal's
        $\ski$. An attacker who compromises the proxy can: (i)~drop
        APBRequired notifications (leading to unresolved halts, not
        silent resumption), (ii)~modify tool call arguments before
        forwarding, or (iii)~suppress tool results. Mitigations:
        proxy integrity (code signing, attestation), and monitoring of
        the APB log.
  \item[M2. Colluding proxy + principal.]
        If the proxy process and the principal collude, the principal
        can sign arbitrary $\Dh$ blocks, and the proxy forwards the
        results. The APB still records the decision non-repudiably
        (T8.2 holds), so the collusion is detectable in post-hoc audit.
\end{description}

The following adversaries are \emph{not} modelled by E5 and are
open; an MCP-security reviewer will ask about each:
\begin{description}[leftmargin=2em, topsep=2pt]
  \item[M3. Proxy bypass.]
        Nothing in the design forces traffic through the proxy. An agent
        or attacker that connects directly to the MCP server is
        ungoverned; ``drop-in'' is only as strong as the network
        topology that makes the proxy the sole path to the server.
  \item[M4. Time-of-check/time-of-use on the approved call.]
        P8's evidence block did not say which call a halt concerns, so a
        signature approved \emph{that a halt occurred}, not \emph{what}.
        The action commitment $\ahash$ closes this for the reference
        flow (the signature now covers tool and arguments; the client
        refuses to run a different call), but it is exercised by unit
        tests, not by an end-to-end experiment, and it is only as strong as
        the party that executes the call.
  \item[M5. Malicious or poisoned tool server, prompt injection.]
        A server that returns crafted results, or an injection that
        causes or hides drift, acts on the agent's side of the proxy.
        The proxy sees tool calls and a drift estimate; it does not
        inspect tool results or prompts.
  \item[M6. Adaptive evasion of the detector.]
        An adversary who keeps $\Dhat$ below the threshold $\theta$ (and
        exploits the burn-in, Limitation~3) is never halted. No
        adaptive attacker was evaluated.
  \item[M7. Denial of service.]
        Flooding the principal with halts, and (in the reference
        interceptor) submitting a bad APB for a pending evidence\_id,
        which \emph{deletes} that pending halt: the call is not executed
        but cannot be approved either.
\end{description}

\subsection{A2A Specification Maturity}

At the time of writing, A2A \citep{google2025a2a} is a draft. The
multi-hop results (T9.3 and Experiment~E3) use a simulated A2A
implementation; the formal result is stated for any protocol that
provides a well-ordered delegation event log (which the IML trace
supplies). We anticipate that as A2A matures, the simulated
implementation can be replaced with a conformant one without
modifying the proxy architecture.

\subsection{Limitations}

\begin{enumerate}[leftmargin=2em, topsep=2pt, itemsep=2pt]
  \item \textbf{Dynamic tool discovery.}
        The proxy entry point hard-codes the five P7 tools. A production
        deployment requires dynamic tool discovery and mirror
        registration, which we treat as an engineering extension.
  \item \textbf{Single governance layer.}
        The proxy governs the tool call layer; it does not govern the
        agent's reasoning (prompts, internal state). Drift at the
        reasoning layer is not visible to the proxy.
  \item \textbf{$\Dhat$ requires burn-in.}
        The IML drift estimator requires a burn-in trace to establish
        $\Azero$. For newly launched agents, the initial $\Dhat$
        is conservative (low drift), meaning the first few calls
        of a genuinely malicious sequence may not trigger a halt.
  \item \textbf{A halt is not forwarded and is not awaited.}
        The design principle is \emph{no authority, no action}: a
        halted call is not forwarded to the server. In the reference
        implementation the halt is returned as a text result
        (Remark~\ref{rem:backward}), so the call completes and nothing
        waits for the principal; the intended blocking wire protocol is
        not implemented. Paper~10 \citep{fernandez2026nbg} treats the
        asynchronous side (timeout semantics, escrow, deferred
        approval); it was itself corrected after an audit found that
        its first release let an APB for one entry resolve another.
  \item \textbf{V4 window versus human latency.}
        V4 rejects an APB whose $t_e$ is older than the replay window
        (default $300\,\si{s}$, configurable per interceptor). A human
        who answers a halt after more time than that is refused as a
        replay; the window must be set to the expected approval time.
  \item \textbf{No real MCP client, server, transport or LLM.}
        Every experiment calls the interceptor in-process with a
        \texttt{MockLLM} and an auto-approving simulated human. There
        is no HTTP+SSE implementation, and no run against a third-party
        MCP client or public MCP server.
  \item \textbf{Benchmark hardware and network conditions.}
        Latency measurements were collected on a single hardware
        configuration (i9-13900HX, 32\,GB RAM) under local,
        in-process conditions ($\Dnet = 0$). Absolute latency values
        will differ under cloud deployments, containerised proxies,
        or cross-network configurations. The windowed monitor is $O(1)$
        per call by construction; the relative ordering of ADMIT and HALT
        was not tested on other hardware.
\end{enumerate}

\subsection{Threats to Validity}

\emph{Internal.} The agent is a deterministic \texttt{MockLLM}; the
$31\%$ halt rate is imposed by its drift schedule. The human is
simulated and always approves, so APB validity measures that local
signatures verify, not approval behaviour. \emph{External.} One
machine (Windows), five toy tools, no third-party client or server, no
live LLM, no user study, and single-run measurements without confidence
intervals. \emph{Construct.} The latency in E1 is an in-process
function call and stands in for, but is not, the overhead of a real MCP
transport. \emph{Statistical.} The adversarial suite is authored by the
same person who wrote the defences. \emph{Comparison.} There is no
baseline: no other guardrail, gateway or policy engine (for example a
rules-based guard or an OPA/Cedar gateway) was evaluated, and the
related work does not survey MCP-specific security work (tool
poisoning, prompt-injection defences), access-control and delegation
systems (capability and credential chaining, macaroons, authenticated
delegation) or enforcement-monitor theory.

\subsection{Revision Note: What the First Release Got Wrong}

An independent audit of the first release found the following; each is
either corrected in this version or stated as a limitation above.
\begin{enumerate}[leftmargin=2em, topsep=2pt, itemsep=2pt]
  \item \textbf{Claims the code did not meet.} The paper said the proxy
        supports HTTP+SSE (no implementation exists) and that
        $p9/\mathrm{apbRequired}$ is sent as a blocking notification that
        a legacy client would ignore and time out on (the halt is
        returned as a text result). Both are withdrawn.
  \item \textbf{V5 was not applied.} The verifier was called without a
        seen-event set. Fixed, with a test.
  \item \textbf{Signature did not cover the call.} $\Es$ carried no tool
        or arguments (TOCTOU). Fixed with the optional $\ahash$.
  \item \textbf{Experiment labels.} E2 is not a ``real agent'' (it uses
        \texttt{MockLLM} and an auto-approving human; the live variant
        was never run), and a latency threshold was named ``the T9.1
        gate''. Both renamed.
  \item \textbf{Theorems.} T9.1 and T9.2 are now stated as what they are
        (by construction; a decomposition); T9.3 is stated under an
        explicit attribution axiom, and its former justification through
        DC.1 is dropped.
  \item \textbf{Scaffolding.} References to ``Sprint~N'' and to sections
        that do not exist in this paper were removed.
\end{enumerate}

\section{Conclusion}
\label{sec:conclusion}

We described the MCP Governance Proxy ($\Proxy$), a design that places
the P8 identity-bound governance protocol at the MCP layer so that it
can be applied to an MCP agent without changing the agent's code, and a
Python reference implementation of its decision logic. We added one
element to P8's evidence block, an optional action commitment $\ahash$,
so that the principal's signature covers which call is approved.

The three results are modest: T9.1 holds by construction, T9.2 is a
decomposition of the halt latency, and T9.3 holds under an explicit
attribution axiom and an unauthenticated delegation chain.

The evaluation is in-process and simulated:
\begin{itemize}[leftmargin=2em, topsep=2pt, itemsep=1pt]
  \item \textbf{E1}: the windowed monitor has a P95 decision overhead of
        $51.8\,\si{\micro\second}$ (an in-memory call, not a real
        transport); the HALT path adds $\approx 10\,\si{\micro\second}$.
  \item \textbf{E2} (\texttt{MockLLM}, simulated human, $5$ seeds
        $\times$ $200$ steps): $310$ HALT events, every APB verifies;
        the live-LLM variant was not run.
  \item \textbf{E3}: the configured delegation chain is copied into the
        evidence block at depths $1$--$5$; the chain is not authenticated.
  \item \textbf{E4}: $0$ exceptions for independent concurrent sessions.
  \item \textbf{E5}: six author-written attacks are rejected; a
        regression suite, not a security measurement.
\end{itemize}

The implementation, available at
\url{https://github.com/chelof100/mcp-governed-agents}, passes $97$
tests ($61$ inherited from P7+P8, $36$ new proxy tests).

\paragraph{Future work.}
Paper~10 \citep{fernandez2026nbg} addresses the asynchronous side:
timeout semantics, escrow-state serialisation and deferred-approval
queues, so that governance events can be resolved without halting the
agent pipeline. It has not been integrated into this proxy.
A second direction is distributed, multi-organisation governance
via a Merkle-chained APB log providing tamper-evident accountability
across organisational boundaries.
A third direction is dynamic tool discovery: the current proxy
hardcodes the tool risk map; a conformant implementation should mirror
the server's tool list dynamically and apply risk scores via a
configurable policy file.
Finally, the pieces needed to turn this design into a demonstrated
system are, in order of importance: an end-to-end evaluation against a
third-party MCP client and real MCP servers over a real transport;
evaluation with real LLMs and tasks, with false positives and a real
or at least latency-modelled approver; authenticated delegation (each
delegator signs the next hop), with branching chains and scope
attenuation; and a comparison against existing guardrail and
policy-engine baselines.

All code and experimental data are available at
\url{https://github.com/chelof100/mcp-governed-agents}.
